# Decision Record 03 — หน้าแอดมินบริหารจัดการข้อมูล

> วันที่: 2026-09-26 · **สถานะ: ACCEPTED**
> ต่อยอดจาก `02-final-decisions.md` (Supabase + Cloudflare)

---

## บริบท

ต้องให้ผู้ดูแลระบบเพิ่ม / ลบ / แก้ไข / นำเข้าคอร์ส แพ็กเกจ ผู้สอน หมวดหมู่
และข้อมูลธนาคาร ได้โดยไม่ต้องแก้โค้ด

ข้อจำกัดที่มีอยู่แล้ว:
- ข้อมูลทั้งหมดเป็นไฟล์ `data/courses.js` ที่อ่านตอน build
- โปรเจกต์ไม่มี auth library และไม่มีฐานข้อมูล
- ADR เดิมเลือก Supabase ไว้แล้ว
- ต้อง deploy บน Cloudflare Pages

---

## การตัดสินใจ 1 — ที่เก็บข้อมูล: Supabase (ตาม ADR เดิม)

**ทางเลือกที่พิจารณา**

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| เขียนทับไฟล์ด้วย Node `fs` | ใช้ได้ทันที ไม่ต้องตั้งอะไร | **Cloudflare Pages เขียนไฟล์ไม่ได้** · ทุก save ทำ git สกปรก · เขียนพลาดแล้วเว็บล้ม |
| SQLite (`better-sqlite3`) | ฐานข้อมูลจริงในเครื่อง | เป็น native module · **รันบน Cloudflare Workers ไม่ได้** |
| **Supabase** | ตรงกับ ADR · deploy ได้ทุกที่ · RLS บังคับสิทธิ์ระดับฐานข้อมูล · ใช้งานเชิงพาณิชย์ได้ | ต้องสร้าง project ก่อน |

**ตัดสินใจ: Supabase**

เหตุผลหลักคือ **Cloudflare Pages ไม่รองรับการเขียน filesystem**
ทางเลือกไฟล์จะทำให้ผู้ดูแลใช้งานได้เฉพาะตอน dev แล้วพังตอน deploy ซึ่งเป็นการสร้าง
หนี้ที่ต้องจ่ายตอนปล่อยของจริง

**ผลกระทบ**
- ต้องสร้าง Supabase project ก่อนหน้าแอดมินจึงจะบันทึกได้
- ระหว่างที่ยังไม่ได้ตั้งค่า ระบบ **fallback ไปอ่านไฟล์เดิม** → เว็บหน้าบ้านยังใช้ได้ครบ
  และ middleware ส่งไปหน้า `/admin/setup` ที่อธิบายขั้นตอน
- `data/courses.js` เปลี่ยนสถานะจาก "แหล่งข้อมูล" เป็น **snapshot** สำหรับเดโมเวอร์ชัน HTML
  (ดึงกลับด้วย `scripts/export-snapshot.mjs`)

## การตัดสินใจ 2 — การยืนยันตัวตน: Supabase Auth + ตาราง `admins`

**ตัวเลือกที่พิจารณา**

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| เขียน session เอง (`crypto.scrypt`) | ไม่ต้องมีบริการภายนอก | ต้องดูแลเองทั้งหมด · เสี่ยงทำผิด · ไม่มี refresh token |
| **Supabase Auth** | session จัดการให้ · ไม่ต้องเก็บรหัสผ่านในระบบเราเลย | ต้องมี project |

**ตัดสินใจ: Supabase Auth**

เหตุผลสำคัญที่สุด: **รหัสผ่านของผู้ดูแลไม่ต้องถูกเก็บในโปรเจกต์เลย**
ผู้ใช้ตั้งเองที่ Supabase Dashboard → รหัสผ่านไม่เคยผ่านเครื่องเรา
ไม่เข้าไฟล์ ไม่เข้า git ไม่เข้า shell history

สิทธิ์ควบคุมด้วยตาราง `admins` ที่อ้าง `user_id` จาก `auth.users`
RLS ของตารางนี้อนุญาตให้แอดมินอ่านได้เฉพาะแถวของตัวเอง

**ผลกระทบ**
- ถ้าล็อกอินแล้วไม่มีแถวใน `admins` → ระบบ `signOut` ทันทีและส่งกลับหน้า login
  พร้อมข้อความว่าไม่มีสิทธิ์ (ป้องกันบัญชีที่มีอยู่แต่ไม่ได้เป็นแอดมิน)
- error การล็อกอินไม่บอกว่าอีเมลถูกหรือรหัสผิด กันการเดา email

## การตัดสินใจ 3 — ชั้นการป้องกัน 3 ชั้น

| ชั้น | กลไก | กันอะไร |
|---|---|---|
| 1 | `middleware.ts` ตรวจ session + เช็คตาราง `admins` ก่อนเข้า `/admin/*` | ผู้ใช้ที่ยังไม่ล็อกอินหรือไม่ใช่แอดมิน |
| 2 | ทุก Server Action เรียก `requireAdmin()` | เรียก action โดยข้ามหน้าเว็บ (ต้องมี session จริงถึงจะถึงขั้นนี้) |
| 3 | RLS policy `using (is_admin()) with check (is_admin())` ทุกตาราง | key หรือ token ที่หลุดมาข้ามโค้ดแอป |

> **ออกแบบเดิมผิดไปหนึ่งจุดและแก้แล้ว:** ร่างแรกใช้ `service_role` key
> ในการตรวจสัทธิ์ ซึ่งทำให้ `auth.uid()` ไม่ทำงานและข้าม RLS ทั้งหมด
> แก้เป็นใช้ **anon key + JWT ของผู้ใช้จาก cookie** ผ่าน `@supabase/ssr`
> ทำให้ RLS ทำงานจริงในชั้นที่ 2 ด้วย
> `service_role` ถูกจำกัดไว้ใช้เฉพาะสคริปต์นอกเว็บ (seed / admin-create / export-snapshot)

## การตัดสินใจ 4 — `cover` เก็บเป็น token ไม่ใช่ class string

**ปัญหา:** `data/courses.js` เก็บ `cover: 'from-emerald-100 to-green-100'`
Tailwind สร้าง CSS ตอน build โดยสแกนซอร์สโค้ด
ถ้าให้ผู้ดูแลพิมพ์ class อิสระในฟอร์ม **CSS จะไม่มี class นั้น** → การ์ดไม่มีสีพื้นหลัง

**ทางเลือก**

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| safelist ทุกคู่สี Tailwind | พิมพ์อะไรก็ได้ | CSS บวมมาก (หลายพัน class) · เปิดช่องให้ทำเว็บพัง |
| **token + map ในโค้ด** | CSS เล็ก · ควบคุมได้ · ผู้ดูแลทำการ์ดพังไม่ได้ | เพิ่มสีใหม่ต้องแก้โค้ด |

**ตัดสินใจ: token (17 สี) + `safelist` ใน tailwind.config.ts**

`app/lib/covers.ts` เป็นแหล่งเดียวของการแมป token → class
มี `tokenFromClass()` แปลงรูปแบบเดิมให้อัตโนมัติตอน seed

**ผลกระทบ**
- ฟอร์มใช้ `CoverPicker` (dropdown + ตัวอย่างสีจริง) ไม่ใช่ช่องพิมพ์อิสระ
- `courseSchema` ปฏิเสธ cover ที่ไม่รู้จัก → ป้องกันทั้งจากฟอร์มและจากการนำเข้า
- เทสต์ยืนยันว่า cover เดิมทั้ง 12 แบบแปลงเป็น token ได้ครบ

## การตัดสินใจ 5 — route group แยกส่วนที่ต้องล็อกอิน

`app/admin/(panel)/` เก็บหน้าที่ต้องล็อกอิน (มี sidebar + guard)
`app/admin/login/` และ `app/admin/setup/` อยู่นอก group

**เหตุผล:** layout ของ `app/admin` จะครอบหน้า login ด้วย ถ้าเรียก `requireAdmin()`
ใน layout จะเกิดวนไม่รู้จบ (redirect กลับไป login ที่ถูก layout บล็อก)

**ผลกระทบ:** route group ไม่เปลี่ยน URL → `/admin/courses` ยังเป็น `/admin/courses`
แต่ต้นไม้ไฟล์ต่างกันหนึ่งระดับ → ต้องระวัง relative import ให้ถูก

---

## การตัดสินใจ 6 — เขียน RLS แยกทีละตาราง ไม่ใช้ loop

ร่างแรกใช้ `do $$ ... foreach t in array array['categories',...]`
เพื่อไม่เขียนซ้ำ 7 ครั้ง

**เหตุผลที่เปลี่ยน:** โค้ดความปลอดภัยที่ตรวจสอบยากคือข้อผิดพลาด
`test.js` ตรวจ RLS ด้วยการ grep `alter table public.X enable row level security`
แต่ 6 ตารางถูกซ่อนใน string ของ `format()` จึง **กรีดไม่เจอ**
→ แก้โดยเขียนแยกทุกตาราง ให้ grep ได้ครบ และมีเทสต์ยืนยันว่าไม่มี loop กลับมา

**ผลกระทบ:** ไฟล์ SQL ยาวขึ้น ~30 บรรทัด · ตรวจสอบได้จริง

## สิ่งที่ยังไม่ตัดสินใจ

| หัวข้อ | เหตุผล |
|---|---|
| อัปโหลดไฟล์ประกอบจริง | ยังไม่มี storage · ต้องคิด path และสิทธิ์กับ private/public |
| ออเดอร์/สมาชิก/Enrollments | ยังเป็น mock ใน localStorage · ต้องมีตารางผู้เรียนก่อน |
| โหมด maintenance มีผลจริง | เก็บค่าไว้แล้วแต่ยังไม่กระทบหน้าสาธารณะ |
| ผู้ดูแลหลายคน | ตอนนี้ตาราง `admins` รองรับหลายแถวอยู่แล้ว แต่ UI ไม่มีให้เพิ่ม |
